# خطة تحويل نظام الإدارة إلى Windows EXE + SQLite

تاريخ البدء: 2026-11-20  
الفرع: feature/windows-exe-sqlite  
النسخة الأساسية: 910bf97507cd5e0c5a64300873e9883ca9cafbb3

## الهدف المعتمد

تسليم برنامج Windows مستقل قابل للتثبيت والتشغيل دون الحاجة إلى متصفح أو Node.js مثبت لدى المستخدم، مع قاعدة SQLite محلية تحفظ البيانات بعد إغلاق البرنامج أو إعادة تشغيل الجهاز، وتبقى سليمة بعد تحديث البرنامج.

## شروط العمل التجاري المعتمدة

1. **الحفظ الدائم:** كل عملية مالية أو تشغيلية ناجحة تُحفظ في SQLite، ولا تعتمد النسخة النهائية على ذاكرة مؤقتة أو localStorage أو IndexedDB كمصدر أساسي للحقيقة.
2. **استمرار البيانات بعد الإغلاق:** إغلاق البرنامج أو Windows لا يمسح القاعدة. عند إعادة التشغيل تُفتح نفس القاعدة.
3. **سلامة العمليات:** تستخدم العمليات المالية معاملات SQLite ذرية؛ إما أن تُحفظ العملية كاملة أو يتم التراجع عنها كاملة.
4. **التحديث دون فقد البيانات:** تحديث EXE لا يحذف قاعدة البيانات ولا يستبدلها بقاعدة فارغة؛ البيانات في مسار ثابت مستقل عن مجلد التثبيت.
5. **ترحيل المخطط:** كل تغيير للجداول يمر عبر migrations مرقمة، مع نسخة احتياطية مُتحقق منها قبل الترحيل.
6. **إلغاء التثبيت:** لا يحذف إلغاء التثبيت بيانات المستخدم تلقائيًا؛ حذف البيانات إجراء منفصل وصريح.
7. **النسخ الاحتياطي:** توجد نسخة يدوية ودورية ونسخة قبل ترقية مخطط القاعدة، مع إمكانية إخراجها إلى وسيط خارجي.
8. **الاستعادة:** تُفحص النسخة قبل الاستعادة وتتم الاستعادة إلى ملف مؤقت قبل استبدال قاعدة التشغيل.
9. **العمل دون إنترنت:** تستمر العمليات المحلية المسموح بها دون اتصال؛ المزامنة لا تستبدل السجل المحلي بصمت.
10. **حدود الحماية:** الحفظ على نفس القرص لا يحمي من تلف القرص أو فقد الجهاز؛ يلزم إخراج نسخة إلى وسيط آخر.

## القرار التقني

- Electron لتغليف واجهة React الحالية.
- SQLite تعمل داخل عملية Electron الرئيسية فقط.
- واجهة React تتصل عبر IPC محدود ومتحقق منه من خلال preload.
- contextIsolation=true وnodeIntegration=false وsandbox=true.
- منع وصول الواجهة إلى filesystem أو SQL أو Node.js مباشرة.
- قاعدة البيانات في مسار app.getPath('userData') ثابت ومستقل عن مجلد تثبيت EXE.
- تفعيل WAL وforeign_keys وbusy_timeout وsynchronous=FULL ومعاملات مالية ذرية.
- النسخ عبر SQLite online backup أو آلية موثوقة تراعي WAL.
- لا تكون IndexedDB مصدر الحقيقة في نسخة Windows النهائية.

## الوضع الحالي المثبت

المستودع الحالي React/Vite وDexie/IndexedDB. طبقة Dexie مستخدمة مباشرة في قاعدة البيانات والخدمات والخطافات وخدمات المزامنة والتخزين. لذلك لا يكفي إضافة Electron وملف SQLite فارغ؛ يجب نقل عمليات القراءة والكتابة والمعاملات والاشتراكات إلى موفر SQLite فعلي.

## التقدم المنفذ في فرع Windows

- أضيفت وثيقة قرار معماري وشروط الحفظ الدائم والتحديث دون فقد البيانات.
- أضيف SQL migration أولي لجداول المؤسسة والفروع والأنشطة والحسابات والمخزون والأطراف والفواتير وبنودها والقيود والصناديق والسندات والأمانات والمستخدمين والتدقيق والمزامنة والعدادات ونقاط البيع والأجهزة والإعدادات.
- القيم المالية والكميات المفهرسة تحفظ كنص عشري لتجنب إدخال تقريب SQLite REAL في أعمدة التخزين، وتحتفظ السجلات كذلك بحمولة JSON كاملة.
- أضيف محرك قاعدة بيانات داخل مجلد Electron: ملف ثابت في مسار بيانات المستخدم، تفعيل WAL وforeign keys وsynchronous=FULL، وسجل migrations مع SHA-256.
- يرفض المحرك تعديل migration سبق تطبيقها، ويأخذ نسخة قبل كل ترقية لاحقة، ثم يفحص integrity_check وforeign_key_check.
- أضيف اختبار Node لمحاكاة إعادة فتح القاعدة، التراجع عن معاملة، وإنشاء نسخة احتياطية عبر SQLite Online Backup API.
- أضيف اختبارَي مخطط SQLite ومحرك التشغيل إلى CI.

**حدود هذا التقدم:** محرك SQLite واختباراته أصبحا موجودين في المستودع، لكن الواجهة وخدمة البيانات لم تتصلا به بعد. لم نضف Electron shell أو IPC أو EXE حتى الآن. كما أن Node يصف واجهة node:sqlite الحالية بأنها Release Candidate؛ لذلك تُعزل خلف طبقة المحرك وتُختبر على إصدار Electron المثبت قبل اعتمادها تجاريًا.

## طبقة المصادقة التي سبقت ربط عمليات ERP

- خدمة المصادقة في العملية الرئيسية متوافقة مع تنسيق PBKDF2-SHA256 المستخدم حاليًا في النظام، وتستخدم مقارنة ثابتة الزمن.
- تحفظ تجزئة كلمة المرور في عمود منفصل ولا تعاد إلى الواجهة.
- جلسات التطبيق رموز عشوائية مؤقتة محفوظة في ذاكرة العملية الرئيسية؛ يجب تسجيل الدخول مجددًا بعد إعادة تشغيل التطبيق.
- يعاد فحص حالة المستخدم وصلاحيات المؤسسة والفرع من SQLite عند طلب هوية الجلسة؛ تعطيل المستخدم يلغي صلاحية الرمز.
- توجد آلية إعداد مدير أولي فقط عندما لا يوجد أي مستخدم في قاعدة المؤسسة.
- القفل بعد خمس محاولات فاشلة لمدة خمس دقائق محفوظ في سجل المستخدم.
- الاختبار يغطي توافق التجزئة والإعداد الأولي وتسجيل الدخول والقفل وانتهاء الرمز وإلغاءه بعد تعطيل الحساب.

**تنبيه:** هذه الخدمة ومحركها موجودان في العملية الرئيسية، لكن واجهة تسجيل الدخول الحالية لم تُحوّل إليها بعد؛ لذلك لم تصبح مصادقة إصدار Windows متصلة تشغيليًا حتى اكتمال ربط شاشة الدخول وترحيل المستخدمين.

## مراحل التنفيذ الإلزامية

### WEX-01: تأسيس سطح Windows الآمن
- [x] إضافة ملف Electron main وpreload آمنين.
- [x] تثبيت مسار بيانات مستخدم ثابت مستقل عن مجلد التثبيت.
- [x] منع النوافذ والتنقل غير المصرح بهما.
- [x] إضافة IPC محدود لقراءة حالة محرك القاعدة فقط، دون تمرير SQL.
- [x] تأجيل IPC النسخ الاحتياطي حتى نقل المصادقة والصلاحيات إلى العملية الرئيسية؛ لا نكشف نسخة البيانات قبل التحقق من صلاحية المستخدم.
- [ ] إضافة اعتمادات Electron وحزمة البناء وتشغيل اختبار Windows.
- نافذة محلية تحمل ملفات dist فقط.
- تعطيل التنقل الخارجي وفتح الروابط الخارجية بعد التحقق.
- إعداد أيقونة التطبيق واسم المنتج وإعدادات البناء.
- عدم كشف IPC عام أو تنفيذ SQL قادم من renderer.

### SQL-01: محرك SQLite ومخطط البيانات
- [x] تعريف مخطط SQL أولي للكيانات التشغيلية الأساسية.
- [x] اختبار أولي للمخطط والمعاملات والاستمرارية والنسخ الاحتياطي عبر SQLite.
- [x] إضافة محرك SQLite ودفتر migrations مع checksum.
- [x] فحص integrity_check والنسخ الاحتياطي قبل ترقية المخطط.
- [ ] تضمين المحرك في Electron الفعلي واختباره على Windows.
- [ ] اختبار SQLite من داخل تطبيق Windows الفعلي.

### DATA-01: نقل طبقة البيانات
- بناء واجهة موحدة لموفر البيانات مع تنفيذ SQLite.
- نقل العمليات المالية الذرية إلى معاملات SQLite.
- نقل الاشتراكات الحية إلى إشعارات آمنة بعد نجاح الكتابة.
- ترحيل Dexie الحالي إلى SQLite دون حذف الأصل.
- مقارنة أعداد السجلات والمجاميع المالية والأرصدة قبل وبعد النقل.

### SEC-01: حماية التطبيق والبيانات
- فرض صلاحيات المستخدم والفرع والمؤسسة في main/data layer.
- التحقق من كل IPC input.
- حماية ملف القاعدة والنسخ الاحتياطية بصلاحيات نظام التشغيل.
- عدم تخزين أسرار تشفير ثابتة داخل ملفات التطبيق.
- تسجيل تدقيق للعمليات الحساسة.

### BACKUP-01: النسخ والاستعادة
- نسخ SQLite بطريقة تراعي WAL.
- نسخة دورية ويدوية ونسخة قبل ترحيل المخطط.
- فحص النسخة قبل اعتمادها واستعادتها.
- توفير تصدير إلى مسار خارجي.

### BUILD-01: حزمة Windows
- بناء x64 installer بصيغة NSIS EXE.
- تثبيت لكل مستخدم أو لكل الجهاز.
- قاعدة البيانات في userData مستقلة عن التحديث وإلغاء التثبيت.
- تثبيت إصدار أحدث لا يزيل البيانات ولا ينشئ قاعدة جديدة بدل القديمة.
- بناء artifact واختباره على Windows.

### QA-01: بوابة القبول
- اختبار تثبيت نظيف وتشغيل أول مرة.
- اختبار البيع والشراء والقيد المزدوج والسند والأمانة.
- التحقق من الأرصدة بعد إغلاق البرنامج وإعادة فتحه.
- إغلاق قسري أثناء معاملة والتحقق من عدم وجود كتابة جزئية.
- إطفاء/إعادة تشغيل Windows والتحقق من استمرار البيانات.
- تثبيت إصدار أحدث والتحقق من بقاء البيانات.
- اختبار ترحيل Dexie والنسخ الاحتياطي والاستعادة.
- اختبار العمل دون إنترنت وإلغاء التثبيت دون حذف البيانات.
- لا إصدار إنتاجي قبل نجاح جميع الاختبارات الحرجة.

## شروط عدم الادعاء بالاكتمال

- وجود EXE وحده لا يعني أن SQLite موصولة.
- إنشاء ملف .sqlite وحده لا يعني أن العمليات تستخدمه.
- اختبار SQL بواسطة Python لا يثبت أن Electron يستخدم قاعدة البيانات.
- نجاح CI على Linux لا يغني عن اختبار تثبيت وتشغيل وتحديث على Windows.
- لا تُحذف Dexie أو بيانات المستخدم القديمة قبل نجاح الترحيل والتحقق والنسخ الاحتياطي.

## المخرج النهائي

ملف تثبيت Windows EXE + قاعدة SQLite محلية فعلية + حفظ دائم + ترقية آمنة + نسخ احتياطي واستعادة + تقرير اختبارات Windows.
