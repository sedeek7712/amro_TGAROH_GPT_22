# خطة توحيد مصادقة Windows مع SQLite

تاريخ الفحص: 2026-11-20  
الفرع: `feature/windows-exe-sqlite`  
الحالة: تنفيذ AUTH-01 إلى AUTH-04 جزئيًا على فرع التطوير؛ لا تزال مصادقة Windows محصورة ولا تعني جاهزية طبقة البيانات.

## 1. القرار المعماري

في نسخة Electron يجب أن تكون قاعدة SQLite وخدمة المصادقة داخل العملية الرئيسية هي المصدر الوحيد لهوية المستخدم والجلسة. لا يجوز أن تمنح مصادقة المتصفح أو Dexie صلاحية دخول بديلة في تطبيق Windows.

تبقى مصادقة الويب/PWA منفصلة وفق مسارها الحالي إلى أن يحدد المشروع صراحةً موفر المصادقة الخاص بكل بيئة.

## 2. ما هو موجود فعليًا

### Electron main

`electron/main.mjs` يعرّف IPC محميًا بـ `assertTrustedMainFrame` للقنوات التالية:

- `erp:auth:setup-status`
- `erp:auth:create-initial-admin`
- `erp:auth:login`
- `erp:auth:me`
- `erp:auth:logout`
- `erp:auth:complete-password-change`

### Preload

`electron/preload.cjs` يعرض واجهة محدودة عبر `contextBridge` ولا يعرض Node أو SQL للواجهة.

### خدمة المصادقة المكتبية

`electron/security/authentication.mjs` تتحقق من كلمة المرور بـ PBKDF2، وتطبق قفلًا بعد خمس محاولات، وتصدر رمز جلسة عشوائيًا محفوظًا في ذاكرة العملية الرئيسية، وتعيد فحص المستخدم والفرع عند استدعاء `getActor`.

### شاشة الدخول والتطبيق

- `LoginScreen.tsx` لا تستدعي جسر Electron حتى الآن؛ بل تستدعي `authService.authenticate` وتقرأ/تكتب `db.users` مباشرة.
- إعداد كلمة مرور المدير الأولي وتغيير كلمة المرور الإلزامي يحفظان المستخدم في Dexie.
- `App.tsx` يستعيد الجلسة عبر `authService.validateSession(liveUsers)` ويهيئ Dexie عند بدء التشغيل.
- الجلسة المكتبية في Electron ليست مستمرة بعد إعادة تشغيل التطبيق؛ الرمز موجود في الذاكرة، وبالتالي يلزم تسجيل دخول جديد بعد إعادة التشغيل، وهذا مقبول أمنيًا ما لم تعتمد سياسة جلسات مختلفة.

## 3. نقطة التوافق الحرجة قبل الربط

مخطط SQLite الأولي يعرّف جدول `users`، لكنه لا ينشئ حساب مدير افتراضيًا. اختبار المصادقة يضيف مستخدم المدير يدويًا إلى قاعدة الاختبار قبل استدعاء `createInitialAdmin`.

لذلك لا يجوز ربط شاشة الإعداد مباشرةً قبل التأكد من أن استيراد بيانات Dexie يرحّل مستخدمي النظام إلى جدول SQLite مع الحفاظ على المعرفات والأدوار والفروع وحالة النشاط، وأن قاعدة التثبيت الجديدة تتبع تدفق تهيئة واضحًا لا يسمح بإنشاء مدير على قاعدة غير مهيأة أو يتجاوز حسابات مستوردة.

كما يجب التحقق من توافق مخطط كلمات المرور القديم مع صيغة PBKDF2 المكتبية. لا يجوز افتراض أن التجزئات القديمة قابلة للتحقق باستخدام الدالة المكتبية؛ يجب إما دعم صيغة قديمة صراحةً باختبار، أو فرض تغيير آمن لكلمة المرور عبر تدفق موثق.

## 4. عقد الواجهة المطلوب

ينبغي إضافة تعريف TypeScript محدود لـ `window.amroDesktop`، يتضمن فقط:

- حالة تشغيل قاعدة البيانات.
- حالة الإعداد الأولي وعدد المستخدمين.
- إنشاء المدير الأولي.
- تسجيل الدخول.
- قراءة actor الحالي بواسطة token والفرع.
- إكمال تغيير كلمة المرور الإلزامي.
- تسجيل الخروج.

يجب أن تكون مدخلات ومخرجات هذه الوظائف typed، وألا تعرض الواجهة كلمة المرور المخزنة أو password hash أو قاعدة البيانات أو SQL.

يجب حفظ رمز الجلسة في ذاكرة الواجهة فقط، وعدم حفظه في localStorage أو Dexie. كل عملية بيانات لاحقة يجب أن ترسل الرمز إلى main، حيث يعاد التحقق من المستخدم والصلاحية والفرع.

## 5. خطة الربط المرحلية

| المرحلة | العمل | اختبار الإغلاق |
|---|---|---|
| AUTH-01 | تعريف أنواع جسر Electron واختبارات شكل الاستجابة | TypeScript يمنع أي استدعاء غير typed |
| AUTH-02 | بناء DesktopAuthAdapter مع كشف بيئة Electron | اختبار المتصفح لا يستدعي الجسر |
| AUTH-03 | ربط شاشة الدخول والإعداد الأولي وتغيير كلمة المرور | نجاح/فشل/قفل/رمز تغيير محدود |
| AUTH-04 | ربط App لاستعادة actor عبر الجسر وإزالة validateSession من مسار Windows | إغلاق التطبيق يلغي الجلسة وإعادة التشغيل تتطلب دخولًا |
| AUTH-05 | توحيد تسجيل الخروج وتبديل الفرع | لا يقبل فرع غير مصرح به |
| AUTH-06 | منع واجهات Windows من استخدام authService/Dexie لمنح الهوية | فحص آلي + اختبارات صلاحيات سلبية |

## 6. متطلبات الأمان الإلزامية

- لا يتم قبول user أو role أو tenantId من renderer بوصفه هوية موثوقة؛ الهوية تستخرج من token داخل main.
- لا يكفي إخفاء الشاشة أو منع الوصول من React؛ كل IPC تجاري لاحق يجب أن يتحقق من الجلسة والدور والفرع في main.
- لا تخزن رموز الجلسات في localStorage أو IndexedDB.
- لا تسجل كلمات المرور أو الرموز في logs.
- لا يُسمح بإنشاء مدير أولي إذا كانت هناك حسابات مستخدمين قائمة غير مهيأة إلا عبر تدفق استرداد موثق.
- لا تُحذف بيانات المستخدمين القديمة ولا يُعاد توليد معرفاتهم خلال ربط المصادقة.
- لا تُعتبر هذه المرحلة مكتملة بمجرد نجاح تسجيل الدخول؛ يجب اختبار أن مستخدمًا غير مخول لا يستطيع تنفيذ IPC أو قراءة بيانات فرع آخر.

## 7. ما لم يتم تنفيذه بعد

هذه الوثيقة توثق نتائج الفحص والقرار، ولا تدعي ربط شاشة الدخول بـ Electron. ما زالت شاشة الدخول وApp يعتمدان على مصادقة المتصفح وDexie. لا يتم تحويل هذا المسار حتى تُنفذ اختبارات التوافق وترحيل المستخدمين وتوحيد عقد الجلسة.

## 8. بوابة الإغلاق

لا تعتبر AUTH مكتملة إلا بعد نجاح:
1. تهيئة أول مدير على قاعدة جديدة فارغة وفق سياسة واضحة.
2. استيراد مستخدمين قدامى دون فقد المعرفات أو الصلاحيات.
3. تسجيل الدخول الصحيح ورفض كلمة المرور الخاطئة.
4. القفل بعد خمس محاولات فاشلة ورفع القفل بعد المدة.
5. تغيير كلمة المرور الإلزامي دون منح جلسة كاملة قبل اكتماله.
6. رفض المستخدم المعطل والفرع غير المصرح به.
7. إلغاء الجلسة عند تسجيل الخروج وإعادة التشغيل.
8. إثبات أن واجهة Windows لا تعتمد على localStorage أو Dexie لتحديد هوية المستخدم.


## 9. بوابة التشغيل المؤقتة في Windows

بعد نجاح تسجيل الدخول، لا يعرض التطبيق وحدات البيع والمخزون والحسابات؛ تظهر شاشة صريحة تمنع المعاملات حتى توصيل مزود بيانات SQLite. هذا ليس إصدارًا نهائيًا ولا يجب تجاوز الحاجز أو تشغيل نسخة العملاء بهذه الحالة. أضيف فحص آلي `scripts/verify_desktop_auth_boundary.mjs` للتأكد من عدم فتح Dexie/IndexedDB في Windows أو استخدامه للمصادقة وتخزين الجلسة في localStorage/IndexedDB.
