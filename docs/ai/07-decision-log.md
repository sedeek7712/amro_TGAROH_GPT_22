# سجل قرارات وموافقات مالك المشروع

هذا الملف هو السجل الرسمي للقرارات التي وافق عليها مالك المشروع. لا تُسجل فيه توصية أو افتراض على أنه موافقة. عند وجود اختلاف، يلزم قرار أحدث وصريح يذكر ما الذي استُبدل.

## قواعد التسجيل
- معرّف فريد لكل قرار: `DEC-YYYY-NNN`.
- التاريخ: تاريخ ظهور الموافقة في المحادثة/التوجيه؛ لا تخترع تاريخًا.
- الحالة: مقترح / معتمد / مرفوض / مستبدل.
- النص المعتمد: اكتب ما وافق عليه المالك فقط.
- النطاق: ما يغطيه القرار.
- الاستثناءات: ما لا يسمح به القرار.
- المرجع: رابط PR أو commit أو وثيقة أو رقم محادثة إن توفر.
- عند تعديل قرار، أضف سجلًا جديدًا واربطه بالقرار السابق بدل محو التاريخ.

- **الحالة:** معتمد
- **موافقة المالك:** `all` لنطاق الأدوات والمحادثات؛ `yes` لحفظ القرارات والموافقات في GitHub.

- **النطاق:** جميع الأعمال المستقبلية في المستودع، مع قراءة التعليمات والوثائق وحالة الفرع وPR وCI قبل الاستكمال، وتحديث سجل القرارات ودفتر التقدم عند التسليم.
- **السبب:** منع فقدان سياق العمل أو تكراره عند الانتقال بين محادثة أو أداة وأخرى.
- **الآثار:** إنشاء بروتوكول استمرارية موحد وسجل قرارات مركزي، وربطهما بتعليمات الوكلاء ودفاتر التقدم.
- **الاستثناءات:** لا يمنح هذا القرار إذنًا بدمج PR، أو تعديل `main` مباشرة، أو تنفيذ تغييرات برمجية/Schema/محاسبية غير معتمدة، ولا يحوّل القرارات التقنية المقترحة إلى قرارات مالك.
- **المرجع:** موافقة المالك في محادثة 2026-11-28؛ تنفيذ التوثيق ضمن PR #25.

## سجل المقترحات والقرارات المحسومة

### DEC-2026-002 — توصيات اعتماد تصميم دليل المنتجات والمتغيرات والوحدات
- **التاريخ:** 2026-11-28
- **الحالة:** معتمد — بموافقة صريحة من المالك بتاريخ 2026-11-28.
- **نص موافقة المالك:** «أعتمد التوصيات الستة في DEC-2026-002 كما هي».
- **نطاق الموافقة:** اعتماد التوصيات الستة والتوجه الوظيفي/الهندسي الوارد في هذا القرار فقط.
- **الاستثناءات الصريحة:** لا تمنح الموافقة إذنًا بالبرمجة أو تعديل Schema أو Migration أو Dexie أو خدمات البيع/الشراء/المخزون أو الحسابات أو البيانات، ولا تمنح إذنًا بدمج PR #26 أو أي PR آخر. أي تنفيذ أو دمج يحتاج موافقة مستقلة محددة.
- **مصدر المقترحات:** توصيات المراجعة الهندسية المعروضة على المالك في المحادثة.
- **النطاق:** حسم قرارات PVAR-002 الستة في القسم 14 من `docs/product/PRODUCT_CATALOG_VARIANTS_DESIGN.md` قبل إغلاق التصميم أو بدء PVAR-003.
- **الخيارات الموصى بها لعرضها على المالك:**
  1. **نطاق الإصدار الأول:** تقسيم التنفيذ إلى مراحل؛ تبدأ المرحلة الأولى بمجموعات المنتجات والمتغيرات والعلامات التجارية، وتؤجل الوحدات البديلة والتحويلات إلى مرحلة لاحقة.
  2. **دقة التحويل:** استخدام نسبة صحيحة (numerator/denominator) وحساب BigInt، والحفاظ على دقة المخزون الحالية ذات الأربع منازل؛ يُرفض التحويل الذي لا يمكن تمثيله بدقة آمنة بدل إنتاج كمية تقريبية أو فرق مخزون صامت.
  3. **باركود وحدات التغليف:** السماح بباركود مستقل للحبة وآخر للكرتون لنفس SKU عند الحاجة؛ يجب أن يحل المسح إلى SKU والوحدة المقصودة معًا.
  4. **أسعار الوحدات:** السماح بسعر بيع/شراء مستقل اختياري لكل وحدة بديلة؛ عند غيابه يُحسب سعر مقترح من سعر الوحدة الأساسية ومعامل التحويل، ويظهر للمستخدم للمراجعة قبل حفظ المستند.
  5. **الصور والخصائص:** صورة لكل SKU، مع استخدام خصائص النشاط الحالية؛ تأجيل صورة المجموعة والتتبع التسلسلي العام إلى مرحلة مستقلة.
  6. **المزامنة:** Windows محلي أولًا، مع استمرار حفظ البيانات المحلية؛ تؤجل مزامنة مجموعات المنتجات والوحدات بين الأجهزة إلى مرحلة مستقلة بعد تصميم عقد المزامنة واختباره، ولا يُعلن دعمها قبل ذلك.
- **الأثر عند الاعتماد:** يسمح بإغلاق PVAR-002 على مستوى القرارات الوظيفية والانتقال إلى إعداد fixtures واختبارات baseline في PVAR-003. لا يسمح وحده بإنشاء Migration 004 أو Dexie v8 أو تغيير خدمات البيع/الشراء/المخزون أو الحسابات؛ تبقى هذه الأعمال خاضعة للخطة والبوابات وموافقة التنفيذ المنفصلة.
- **طريقة الحسم:** حُسم القرار بموافقة المالك الصريحة على التوصيات الستة كما هي بتاريخ 2026-11-28.
- **الخطوة التالية:** تحديث حالة PVAR-002 إلى تصميم معتمد، ثم إعداد خطة تنفيذ مستقلة لـ PVAR-003 (fixtures واختبارات baseline على بيانات اصطناعية) وعرض نطاقها وملفاتها واختباراتها ومخاطرها على المالك. لا تبدأ PVAR-003 قبل موافقة تنفيذ مستقلة.


### DEC-2026-003 — تنفيذ PVAR-003 (fixtures واختبارات baseline)

- **الحالة:** معتمد
- **موافقة المالك:** «موافق بصفتك خبير وفريق تطوير متكاملة».

- **ضوابط الاختبار:** استخدام مجلد SQLite مؤقت مستقل وبيانات اصطناعية فقط. تكون كمية المخزون الافتتاحية صفرًا لتجنب إنشاء قيد افتتاحي تلقائي. يجب مقارنة الحسابات والأرصدة والصناديق والقيود قبل الاختبار وبعده.
- **الاستثناءات:** لا تشمل الموافقة PVAR-004 أو أي مرحلة لاحقة، ولا إنشاء ProductFamily أو Variants أو Brand أو ProductUnit في قاعدة البيانات، ولا تعديل أي شاشة أو خدمة تشغيلية.
- **المرجع:** محادثة 2026-11-28؛ فرع `test/pvar-003-product-baseline`؛ PR #27.
- **نتيجة التنفيذ:** اكتملت fixtures واختبارات baseline ضمن النطاق، واجتازت وظائف CI الثلاث على HEAD `9e36bedcdee764cfd07003129bb2620872daa424` في run `46087652146`. دُمج PR #27 بموافقة المالك بطريقة Squash إلى main في commit `b3def57cc6247c1fe7a58ad688612648dc01bedc`.
- **حالة القرار:** نُفذ نطاق DEC-2026-003 وأُغلق PR الخاص به؛ لا يعني ذلك اعتماد ميزات المجموعات والمتغيرات أو بدء PVAR-004.
- **الخطوة التالية:** لا مرحلة لاحقة مأذون بها تلقائيًا؛ أي بدء PVAR-004 أو تعديل Schema أو الخدمات التشغيلية يحتاج موافقة مستقلة.
