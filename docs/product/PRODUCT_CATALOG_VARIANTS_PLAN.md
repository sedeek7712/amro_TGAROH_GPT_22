# خطة تنفيذ دليل المنتجات والمتغيرات ووحدات القياس
## PRODUCT CATALOG, VARIANTS & UNITS IMPLEMENTATION PLAN

- **معرّف الخطة:** TOOFAN-PRODUCT-002
- **يرتبط بالمواصفات:** PRODUCT_CATALOG_VARIANTS_SPEC.md
- **الحالة:** خطة مقترحة؛ لا توجد موافقة على بدء تعديل الكود حتى اعتماد التصميم الهندسي والبوابات
- **قاعدة العمل:** فرع مستقل لكل مرحلة تنفيذية أو مجموعة تغييرات مترابطة، وPR واضح إلى main.

## 1. طريقة استخدام الخطة

- لا تنفذ مهمة قبل قراءة المواصفات ودفتر الاستكمال.
- المهام المكتملة لا تعاد من البداية؛ تحقق من الأدلة فقط.
- لا تُعلّم مهمة بأنها مكتملة دون Commit واختبارات أو مبرر موثق لعدم الاختبار.
- إذا احتاجت مهمة قرارًا من المالك، أوقف الجزء المتأثر وسجل السؤال والخيارات والأثر.
- لا تنفذ Migration أو تغييرات مالية أو تعديل بيانات حقيقية قبل الموافقة المطلوبة.
- يجوز تقسيم أي مهمة إلى PRs أصغر إذا قلل ذلك المخاطر، بشرط بقاء معرفات المهام وروابطها.

## 2. مراحل التنفيذ وبوابات المرور

### PVAR-001 — تدقيق الوضع الحالي
**الحالة:** مكتملة كتدقيق قراءة فقط على main عند الالتزام b1352053bab7f5769d0620843245a4791c6012f6.

يشمل تعريفات Product وProductBatch وInvoiceItem، شاشة InventoryManager ونقطة البيع، مخطط SQLite والجداول ذات الصلة، خدمة المخزون وخدمة حفظ الأصناف ومسار الفاتورة، والبحث عن نموذج Parent/Variant/SKU وUOM conversion.

**دليل الاكتمال:** النتائج موثقة في قسم خط الأساس داخل المواصفات. يجب تكرار التدقيق إذا تغير HEAD قبل التنفيذ.

### PVAR-002 — اعتماد التصميم التقني التفصيلي
**الحالة:** لم تبدأ — البوابة التالية.

المخرجات المطلوبة:
- ERD يوضح المنتج البسيط ومجموعة المنتج وSKU والخيارات والعلامة والوحدات والتحويلات.
- قرار واضح حول بقاء Product الحالي هو SKU، والعلاقة الاختيارية بالمجموعة.
- عقود TypeScript وواجهات dataService وIPC.
- تصميم SQLite migration وDexie schema version، مع خطة توافق.
- قواعد uniqueness بعد فحص البيانات الحالية.
- توضيح دلالة quantity وunit القديمة والجديدة.
- خطة احتساب base quantity والتكلفة والدفعات والمرتجعات.
- أمثلة بيانات قبل/بعد واختبارات قبول.

**بوابة:** مراجعة المالك والموافقة الصريحة قبل أي تغيير Schema.

### PVAR-003 — تجهيز مجموعة الاختبارات والبيانات الاصطناعية
- بناء fixtures لصنف بسيط وصنف له متغيرات ودفعات وصلاحية ووحدات مختلفة.
- إضافة بيانات اختبار متعددة الأنشطة والمؤسسات عند الحاجة.
- وضع اختبارات regression للمنتجات والفواتير الحالية قبل تعديل المجال.
- توثيق الأوامر والنتائج الفعلية.
- عدم استخدام قاعدة بيانات إنتاج أو بيانات عملاء حقيقية.

**القبول:** اختبارات baseline قابلة للتشغيل وتفشل عند كسر سلوك حالي مهم.

### PVAR-004 — إضافة نموذج البيانات والتخزين المتوافق
- تنفيذ Migration مرقمة بعد الموافقة.
- تحديث Dexie schema ومسار SQLite كلٌ وفق عقده.
- إضافة العلاقات والقيود والفهارس اللازمة.
- تحديث القراءة والكتابة والتصدير والاستيراد والنسخ الاحتياطي.
- إبقاء منتجات legacy بدون family وبدون تغيير المعرفات.
- جعل Migration قابلة للتكرار وآمنة ولا تنشئ مجموعات بالتخمين.

**القبول:** اختبارات Migration من القاعدة القديمة والجديدة، ومقارنة أعداد السجلات والكميات والدفعات والقيم.

### PVAR-005 — خدمات المجال والصلاحيات
- عمليات إنشاء وتعديل وأرشفة مجموعات المنتجات.
- إدارة السمات والخيارات والمتغيرات وSKU.
- تحقق الخادم من tenant والفرع والنشاط والصلاحيات.
- منع التكرار غير المسموح به.
- معاملات ذرية عند إنشاء مجموعة ومجموعة SKU معًا.
- تسجيل التدقيق وOutbox عند انطباق بنية النظام.

**القبول:** لا يستطيع renderer تجاوز قواعد المجال، ولا تحفظ بيانات جزئية عند الفشل.

### PVAR-006 — واجهة إدارة المنتجات
- إبقاء نموذج المنتج البسيط مختصرًا.
- إضافة مسار اختياري لإنشاء مجموعة ومتغيراتها.
- معاينة تركيبات المتغيرات قبل الحفظ.
- تحرير SKU منفردًا وأرشفته دون حذف تاريخه.
- إظهار الباركود والكود والصورة والمخزون والسعر لكل SKU.
- دعم RTL ورسائل تحقق واضحة.

**القبول:** مستخدم غير تقني يستطيع إضافة صنف عادي دون المرور بخيارات المتغيرات، وإضافة مجموعة متغيرات دون التباس بين الأب وSKU.

### PVAR-007 — البحث والباركود ونقطة البيع POS
- البحث عن SKU بالاسم والكود والباركود.
- مسح باركود المتغير وإضافته مباشرة للسلة.
- اختيار المتغير عند فتح مجموعة.
- إظهار خياراته في السلة والإيصال والفاتورة.
- منع بيع SKU مؤرشف أو غير متاح أو منتهي الصلاحية وفق القواعد الحالية.
- الحفاظ على ربط كل بند بالفاتورة باستخدام SKU id.

**القبول:** كل عملية بيع تخصم من SKU الصحيح فقط وتظهر هوية المتغير على المستند.

### PVAR-008 — الوحدات والتحويلات والمشتريات والمرتجعات
- تعريف وحدة المخزون الأساسية ووحدات البيع/الشراء.
- تحويل الكميات إلى الوحدة الأساسية داخل خدمة المجال.
- حفظ وحدة المستند ومعامل التحويل والكمية الأساسية كلقطة تاريخية.
- تحديث تدفقات الشراء والبيع والمرتجع دون تفسير خاطئ للبيانات القديمة.
- احتساب تكلفة المخزون وفق السياسة الحالية مع تحويل صحيح.
- اختبار المرتجع بعد تعديل معامل التحويل.

**القبول:** سيناريو 2 كرتون × 24 ثم بيع 3 حبات ثم بيع كرتون يعطي 45 ثم 21 حبة، مع تطابق البنود والخصم والتكلفة.

### PVAR-009 — الخصائص المتخصصة والدفعات والصور
- مراجعة عرض خصائص الصيدلية والمواد الغذائية وقطع الغيار والمعدات.
- إبقاء FEFO والصلاحية ومنع بيع المنتهي.
- ربط كل Batch بـ SKU، لا بالمجموعة الأب.
- الحفاظ على صور SKU الحالية ودراسة صورة المجموعة.
- عدم إضافة تتبع تسلسلي فردي أو ضمان متقدم دون اعتماد نطاقه.

**القبول:** كل خاصية تظهر فقط عند انطباقها ولا تكسر بقية الأنشطة.

### PVAR-010 — التقارير والتصدير والاستيراد والنسخ الاحتياطي
- تجميع تقارير المجموعة من SKU دون احتساب مزدوج.
- إظهار مستوى التجميع في التقارير.
- تحديث صيغ التصدير والاستيراد والنسخ الاحتياطي والاستعادة.
- دعم بيانات legacy التي لا تحتوي مجموعات أو وحدات تحويل.
- التحقق من الصور والمراجع بعد الاستعادة.

**القبول:** backup/restore يحافظ على العلاقات والأعداد والمجاميع والملفات المرتبطة.

### PVAR-011 — اختبارات الانحدار والأمان والتوافق
تشمل اختبارات Product وSKU والخيارات والتفرد، Dexie وSQLite، البيع والشراء والمرتجعات والوحدات والتحويل، المخزون والدفعات والصلاحية والتكلفة، القيود المزدوجة والذرية ومنع التكرار، الصلاحيات وعزل المؤسسة والفرع والنشاط، التوافق مع الفواتير والمنتجات القديمة، Migration وrollback وbackup/restore، والبناء والفحوص المعمارية حسب package.json وCI الحالي.

**القبول:** نتائج موثقة لكل أمر اختبار وcommit؛ لا ادعاء باختبار Windows يدوي دون جهاز واختبار فعلي.

### PVAR-012 — مراجعة المالك والقبول والإصدار
- عرض خطوات اختبار واضحة لرحلة المنتج البسيط والمتغيرات والوحدات.
- عرض مثال شراء وبيع ومرتجع.
- عرض تقرير المخزون والقيد المحاسبي المرتبط دون تغيير الحسابات.
- تسليم سجل التغييرات والاختبارات والقيود المعروفة.
- فتح PR نهائي أو مجموعة PRs مرتبة.
- انتظار موافقة المالك؛ لا دمج تلقائي.

**القبول:** موافقة مالك المشروع على السلوك ونتائج الاختبار، ثم موافقة مستقلة على الدمج.

## 3. شروط توقف إلزامية

أوقف المهمة وسجل البوابة المفتوحة عند:
- عدم وضوح طريقة حساب الكمية أو التكلفة في الفواتير القديمة.
- تعارض SKU/باركود موجود مع قاعدة uniqueness المقترحة.
- حاجة تغيير معادلات محاسبية أو طريقة تقييم المخزون.
- احتمال تعديل أو فقد بيانات أو دفعات أو فواتير.
- اختلاف غير مفهوم بين Dexie وSQLite.
- فشل backup/restore أو rollback.
- تجاوز صلاحيات أو تسرب بيانات بين مؤسسة/فرع/نشاط.
- حاجة قرار يغير نطاق المشروع.

## 4. قواعد الفروع وطلبات المراجعة

- لا تعديل مباشر على main.
- اسم الفرع يبدأ مثلًا بـ feat/product- أو fix/product- أو test/product-.
- اجعل PR صغيرًا ومحددًا قدر الإمكان.
- لا تدمج PR دون موافقة المالك.
- افحص CI على HEAD النهائي، لا على commit قديم.
- حدّث دفتر الاستكمال بعد كل مرحلة وقبل تسليم المهمة لأداة أخرى.

## 5. قالب تسليم كل مهمة

في وصف PR أو تقرير التسليم اكتب: معرف المهمة PVAR، الهدف والسلوك الذي تغير، الملفات والطبقات المتأثرة، الملفات/السلوكيات التي لم تتغير خصوصًا الحسابات والبيانات القديمة، الاختبارات المنفذة ونتائجها، SHA للـ commit والفرع، حالة CI، المخاطر والقرارات المفتوحة، ونقطة الاستكمال التالية.
