# PVAR-004B-1 — خطة تنفيذ تخزين الوحدات البديلة

- التاريخ: 2026-11-28
- الحالة: **خطة مقترحة للمراجعة فقط — لم يبدأ التنفيذ**
- المستودع: `sedeek7712/amro_TGAROH_GPT_22`
- الفرع المقترح للتنفيذ لاحقًا: `feat/pvar-004b-1-product-units-storage`
- نقطة البداية المقترحة: آخر `main` وقت منح موافقة التنفيذ، وليس فرع PR #30 أو PR #31.
- مراجع التصميم: `PRODUCT_CATALOG_UNITS_PVAR_004B_REFINED_DESIGN.md` و`PRODUCT_CATALOG_UNITS_PVAR_004B_ACCEPTANCE_TESTS.md`.
- مرجع القرارات: DEC-2026-002 وDEC-2026-005 وDEC-2026-006.

## 1. الهدف

إضافة مكان آمن لتخزين وحدات القياس البديلة المرتبطة بكل SKU في مساري SQLite وDexie، مع دعم الترقية والنسخ الاحتياطي والاستعادة، دون تشغيل الوحدات داخل البيع أو الشراء أو المخزون في هذه المرحلة.

**مثال:** إذا كانت وحدة المخزون الحالية للصنف «كرتون»، تبقى كما هي. يمكن لاحقًا تعريف وحدة بديلة أخرى مرتبطة بها، لكن هذه المرحلة لا تحول الأرصدة ولا تخصم أو تضيف مخزونًا.

## 2. النطاق المسموح في المرحلة الأولى

1. جدول SQLite جديد للوحدات البديلة.
2. مخزن Dexie جديد للوحدات البديلة.
3. TypeScript type موحد للوحدة البديلة.
4. فحوص صحة البيانات عند الاستيراد والاستعادة.
5. تضمين الوحدات في تصدير واستيراد JSON والنسخ الاحتياطي.
6. اختبارات ترقية قواعد قديمة وجديدة، والعلاقات، والنسخ الاحتياطي والاستعادة، وتكافؤ SQLite وDexie.

لا توجد في هذه المرحلة شاشة لإدارة الوحدات، ولا خدمة تشغيل بيع/شراء، ولا تحويل كميات، ولا بحث باركود في POS.

## 3. نموذج البيانات المقترح

### 3.1 ProductUnit

الجدول/المخزن `product_units` / `productUnits` يمثل **الوحدات البديلة فقط**. لا نضيف سجلًا للوحدة الأساسية؛ مصدر الوحدة الأساسية هو `Product.unit` الحالية، وهي وحدة المخزون الفعلية للصنف.

الحقول المرشحة:

- `id`: معرّف ثابت.
- `tenantId` و`productId`: مالك الوحدة وSKU المرتبط بها.
- `code`: رمز الوحدة ضمن الصنف.
- `nameAr`، و`nameEn` اختياري إذا كان النمط الحالي يتطلبه.
- `baseUnitsNumerator` و`baseUnitsDenominator`: عددان صحيحان موجبان، في أبسط صورة.
- `barcode` و`normalizedBarcode`: اختياريان؛ تحفظ الأصفار البادئة ولا تحول القيمة إلى رقم.
- `sellPrice` و`purchasePrice`: اختياريان ومستقلان، ولا يدخلان في أي عملية تشغيلية بهذه المرحلة.
- `isActive` وحقول الإنشاء والتحديث وفق نمط المشروع.

قيود أساسية:

- FK مركب يحمي tenant ويضمن أن المنتج موجود.
- numerator وdenominator أكبر من صفر.
- لا توجد سلسلة تحويلات؛ كل معامل مباشر نسبةً إلى وحدة المخزون الحالية.
- لا يوجد `isBaseUnit`؛ هذا المخزن لا يكرر الوحدة الأساسية.
- لا حذف فعلي للوحدة المرتبطة لاحقًا بمستندات؛ لكن دورة التعطيل ستُنفذ في مرحلة خدمات الكتالوج، وليست واجهة في المرحلة الأولى.
- لا نفرض قيد تفرد باركود على البيانات القائمة قبل وجود فحص تكرارات آمن وسياسة تعارض معتمدة. يمكن إضافة فهرس بحث غير فريد فقط إذا أثبتت الحاجة إليه.

### 3.2 بوابة الأسعار قبل تثبيت الأعمدة

ثبت في التدقيق أن مقاييس تخزين بعض حقول السعر والتكلفة ليست موحدة بين المسارات الحالية. لذلك قبل كتابة migration يجب إكمال جدول mapping موثق لحقول سعر البيع وسعر الشراء وتكلفة الدفعة وسعر سطر الفاتورة في SQLite وDexie.

لا يُسمح باختيار `MONEY_SCALE` أو `QTY_SCALE` افتراضيًا لكل الأسعار. إذا لم يكتمل هذا التتبع، تتوقف إضافة أعمدة السعر إلى الجدول وتُعرض نقطة القرار للمالك قبل أي تعديل Schema. لا نغير المقاييس الحالية أو طريقة تقييم المخزون.

## 4. الإصدارات والترقية

آخر ما تحقق من `main` وقت إعداد الخطة:

- آخر SQLite migration المطبقة هي 004، ويختبرها `product_catalog_metadata.test.mjs` عبر `MAX(version) = 4`.
- آخر Dexie schema هو الإصدار 8، وفيه مخازن العلامات والمجموعات وبيانات SKU.

الإصدارات المرشحة فقط:

- SQLite: `005_product_units.sql`.
- Dexie: `version(9)`.

يجب إعادة فحص أعلى رقم migration وDexie على commit التنفيذ الفعلي قبل الكتابة. لا تعدل migrations 001–004 ولا تعِد استخدام أرقامها.

سلوك الترقية:

- إنشاء جدول/مخزن وحدات فارغ عند ترقية قاعدة قديمة.
- لا تنشئ وحدة بديلة افتراضية لأي منتج قديم.
- لا تغير `Product.unit` أو الأرصدة أو الدفعات أو الفواتير أو القيود.
- ترقية SQLite يجب أن تكون داخل آلية migrations الحالية، مع rollback تلقائي عند الفشل.
- ترقية Dexie لا تحذف ولا تعيد كتابة سجلات المنتجات القديمة.

## 6. ترتيب التنفيذ عند صدور موافقة مستقلة

### المرحلة A — خط أساس وفحص ما قبل التعديل

1. إعادة قراءة تعليمات المشروع وسجل القرارات ووثائق PVAR-004B.
2. التأكد من أن فرع التنفيذ يبدأ من أحدث `main`، وليس من PR #30 أو #31.
3. التحقق من آخر migration وإصدار Dexie.
4. إعداد جدول mapping للأسعار؛ لا نتجاوز هذه البوابة إذا بقيت غير محسومة.
5. تسجيل قائمة الملفات الفعلية وSHA قبل التعديل.

### المرحلة B — SQLite

1. إضافة migration 005 فقط بعد إعادة التحقق من الرقم.
2. إنشاء جدول الوحدات البديلة مع FK مركب للـ tenant/product.
3. إضافة قيود المعامل الموجب والفهارس الضرورية فقط.
4. تحديث فحص مخطط SQLite والنسخة الاحتياطية ليتعرف على الجدول الجديد.
5. لا تغيير في جداول المنتجات أو الفواتير أو المخزون أو المحاسبة.

### المرحلة C — Dexie والأنواع

1. إضافة `ProductUnit` إلى `src/types/erp.ts`.
2. إضافة `productUnits` إلى كلاس قاعدة البيانات.
3. إضافة Dexie v9 store، مع الإبقاء على مخازن v1–v8 كما هي.
4. لا upgrade callback يملأ وحدات افتراضية أو يعدل المنتجات.

### المرحلة D — النسخ الاحتياطي والاستعادة

1. SQLite JSON export: تصدير قائمة الوحدات ضمن tenant الحالي.
2. JSON import: قبول غياب القائمة في النسخ القديمة وتحويلها إلى قائمة فارغة.
3. التحقق من id وtenantId وproductId والمعاملات والعلاقات والتكرار قبل أي كتابة.
4. استعادة SQLite بترتيب يحترم FK: المنتجات أولًا، ثم الوحدات البديلة.
5. Dexie export/import: تضمين `productUnits` داخل نفس مسار المعاملة الذرية.
6. Native SQLite backup: الملف يحتوي الجدول تلقائيًا؛ يجب تحديث verifier لاشتراط الجدول في النسخ الحديثة مع الحفاظ على قبول النسخ القديمة وفق آلية الإصدار المعتمدة.
7. التأكد من checksum والعدّادات وفحص FK بعد الاستعادة.

### المرحلة E — الاختبارات والبوابة

- SQLite: قاعدة جديدة، ترقية 004→005، rollback عند فشل migration، FK، معاملات موجبة، عزل tenant.
- Dexie: ترقية 8→9، قاعدة جديدة، بقاء جميع مخازن v8 وسجلات المنتجات كما هي.
- Backup/restore: نسخة حديثة، ونسخة قديمة بلا `productUnits`، واستعادة ثم إعادة فتح قاعدة الاختبار.
- التكافؤ: نفس بيانات الوحدات ونتائج التحقق في SQLite وDexie.
- عدم التأثير: مقارنة أعداد المنتجات والدفعات والفواتير والقيود والأرصدة قبل وبعد الترقية.
- تشغيل CI المطلوب: `verify`, `sqlite-electron-runtime`, `windows-exe-preview`، ثم مراجعة نتائج كل وظيفة.
- لا نعلن نجاحًا قبل وجود نتائج فعلية وروابط CI.

## 7. معايير قبول المرحلة الأولى

لا تعتبر المرحلة مكتملة إلا إذا تحققت كلها:

1. وحدة بديلة يمكن تخزينها وربطها بـ SKU وtenant الصحيحين.
2. لا يمكن حفظ معامل صفر أو سالب.
3. لا يمكن ربط الوحدة بصنف في tenant آخر.
4. لا توجد وحدة أساسية مكررة داخل `product_units`.
5. ترقية SQLite وDexie لا تغير سجلًا قديمًا أو رصيدًا أو فاتورة.
6. النسخ القديمة التي لا تحتوي قائمة الوحدات تستعاد دون خطأ وتنتج قائمة وحدات فارغة.
7. النسخ الحديثة تحتفظ بكل الوحدات بعد export/restore.
8. فشل الاستعادة لا يترك بيانات جزئية.
9. اختبارات SQLite وDexie وCI كلها ناجحة.
10. لا يتغير البيع أو الشراء أو المخزون أو المرتجعات أو الحسابات أو الضرائب أو العملات.

## 8. ما هو خارج المرحلة الأولى

- إنشاء/تعديل/تعطيل الوحدات من واجهة المستخدم.
- خدمة تحويل BigInt في البيع أو الشراء.
- تعديل `InvoiceItem` أو إضافة snapshots.
- ربط `invoiceItemId` بخصومات المخزون والدفعات.
- تعديل المرتجعات أو FIFO/FEFO أو التكلفة.
- البحث بالباركود في POS أو فرض unique barcode على البيانات القائمة.
- مزامنة الوحدات أو أي خدمة سحابية.
- تغيير المحاسبة أو الضرائب أو العملات أو أي سياسة تقييم مخزون.

هذه العناصر مراحل لاحقة وتتطلب موافقات مستقلة.

## 10. قرار المالك المطلوب قبل التنفيذ

هذه الوثيقة **خطة فقط**. لا تمنح إذنًا بإنشاء فرع تنفيذ أو تعديل ملفات التطبيق أو إنشاء migration أو تشغيل اختبارات على قاعدة بيانات المستخدم أو فتح PR دمج.

عند اعتماد الخطة لاحقًا، تكون الموافقة المطلوبة محددة هكذا: «أوافق على تنفيذ PVAR-004B-1 وفق هذه الخطة وعلى فرع مستقل من أحدث main، مع اختبارات اصطناعية فقط، ودون دمج أو تغيير أي نطاق آخر».

أي إضافة خارج قائمة الملفات والنطاق أعلاه تتوقف وتعود للمالك قبل تنفيذها.
