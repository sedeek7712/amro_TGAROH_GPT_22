# جرد أولي لاعتماد النظام على Dexie قبل نقل البيانات إلى SQLite

تاريخ الفحص: 2026-11-20  
الفرع: `feature/windows-exe-sqlite`  
مرجع PR: #2  
الغرض: توثيق نقاط الاعتماد التي ثبتت من قراءة ملفات الفرع نفسه، قبل تنفيذ أي تحويل قد يؤثر على البيانات المالية.

> هذا جرد معماري أولي موثق، وليس ادعاءً بأن كل استخدامات Dexie في المشروع قد أُحصيت بعد. يجب استكمال البحث على كامل شجرة الفرع ومراجعة كل خدمة ومكوّن قبل اعتماد خطة النقل النهائية.

## 1. النتيجة التنفيذية

- `src/services/dataService.ts` يعرّف عقد `IDataService` ويشمل العمليات التجارية والمحاسبية، لكنه في نهاية الملف يربط `dataService` فعليًا بـ `dexieDataService`.
- `src/services/dexieDataService.ts` ينفذ العقد باستخدام جداول Dexie مباشرة، ويحتوي على منطق الصلاحيات والفروع والتحقق المالي والتسلسلات والمعاملات متعددة الجداول.
- `src/hooks/useLiveDexie.ts` يقرأ من `db` مباشرة ويستخدم `liveQuery` لإعادة تحديث واجهة React، كما يعتمد على `authService` ومرشحات صلاحيات الفروع.
- `src/db/erpDatabase.ts` يعرّف قاعدة `MultiActivityErpDB` وجداولها وإصداراتها وترحيل قاعدة IndexedDB القديمة.
- `electron/main.mjs` يفتح SQLite ويعرض حالة المحرك ومداخل المصادقة عبر IPC، لكنه لا يعرض بعد عمليات CRUD التجارية أو اشتراكات التغييرات.
- `electron/preload.cjs` يعرض وظائف حالة التشغيل والمصادقة فقط؛ لا توجد فيه واجهة بيانات تجارية.
- لذلك فإن وجود SQLite وElectron لا يعني أن عمليات النظام التجارية تستخدم SQLite حاليًا.

## 2. الملفات التي تمت قراءتها مباشرة من الفرع

| الملف | ما ثبت من محتواه | أثره على النقل |
|---|---|---|
| `src/services/dataService.ts` | عقد IDataService ثم تصدير dexieDataService بوصفها dataService | يجب إنشاء موفر Windows فعلي وعدم إبقاء التصدير مرتبطًا بـ Dexie في نسخة Windows |
| `src/services/dexieDataService.ts` | تهيئة Dexie، ترحيل localStorage، RBAC، فروع، حسابات، مخزون، أطراف، معاملات وجداول متعددة | نقل قواعد العمل والمعاملات دون تغيير نتائجها |
| `src/hooks/useLiveDexie.ts` | liveQuery واستعلامات مباشرة لجداول المنتجات والفواتير والحسابات والقيود والأطراف والصناديق والسندات والأمانات والمستخدمين والتدقيق والمزامنة والفروع | يلزم بديل اشتراك/إبطال cache من SQLite IPC |
| `src/db/erpDatabase.ts` | مخطط Dexie v1-v5 وترحيل AlharajErpDB | مصدر مهم لفهم شكل البيانات القديمة، وليس قاعدة Windows النهائية |
| `electron/main.mjs` | SQLite runtime، فحص حالة القاعدة، IPC للمصادقة فقط | إضافة خدمات مجال محددة داخل main بعد تصميمها واختبارها |
| `electron/preload.cjs` | جسر آمن محدود للمصادقة وحالة التشغيل | توسيع الجسر بوظائف محددة، لا تمرير SQL أو filesystem |
| `package.json` | Dexie ما زالت dependency؛ Electron entry هو electron/main.mjs؛ إعداد NSIS يحتفظ ببيانات المستخدم عند إلغاء التثبيت | لا نحذف Dexie قبل اكتمال ترحيل بيانات المستخدم واختبار التوافق |

## 4. قواعد لا يجوز كسرها أثناء النقل

- كل عملية مالية مركبة يجب أن تتم في معاملة SQLite واحدة داخل العملية الرئيسية.
- لا يسمح للواجهة بإرسال SQL خام أو أسماء جداول حرة أو استعلامات قابلة للتنفيذ.
- يجب التحقق في main من هوية الجلسة والمؤسسة والفرع والصلاحية لكل أمر مالي.
- يجب أن يكون إنشاء الفاتورة/القيد/خصم المخزون/الصندوق/Outbox عملية ذرية حسب قواعد المجال الفعلية.
- يجب الحفاظ على منع التكرار idempotency وتسلسل الأرقام وعدم إعادة استخدام رقم مستند.
- يجب عدم السماح بتعديل أو حذف القيد المرحّل؛ التصحيح يكون بقيد عكسي حسب القواعد الموجودة.
- لا يُحذف Dexie أو IndexedDB ولا يُمسح أي تخزين قديم قبل نسخة احتياطية قابلة للاستعادة، وترحيل متحقق، ومقارنة عدد السجلات والمجاميع المالية لكل مؤسسة وفرع وعملة.
- يجب عدم تهيئة قاعدة تشغيل جديدة تلقائيًا إذا تعذر فتح قاعدة المستخدم الحالية؛ يظهر خطأ واضح ولا يتم إنشاء قاعدة بديلة صامتًا.

## 5. ملاحظات فنية عالية الأهمية

### أ. عقد البيانات غير كافٍ وحده

وجود `IDataService` خطوة مفيدة، لكن بعض المكونات تستورد `dexieDataService` مباشرة، وبعض الخطافات تتعامل مع `db` و`liveQuery` مباشرة. لذلك لا يمكن اعتبار تبديل `dataService` وحده عملية نقل مكتملة.

### ب. التفاعلية ليست مجرد CRUD

الخطافات الحالية تعيد القراءة تلقائيًا عند تغير جداول IndexedDB. يجب تصميم بديل SQLite يرسل إشعارات تغيّر محددة من main بعد نجاح المعاملة، ثم تعيد الواجهة تحميل الاستعلام المناسب. لا يجوز بث بيانات غير مصرح بها أو اعتبار إشعار الواجهة مصدر الحقيقة.

### ج. الصلاحيات يجب أن تنتقل إلى الحد الآمن

التحقق الموجود داخل Dexie renderer لا يكفي لحماية قاعدة SQLite؛ لأن renderer ليس حدًا أمنيًا موثوقًا. يجب إعادة التحقق في main باستخدام جلسة موثقة وبيانات المستخدم المخزنة في SQLite.

### د. المصادقة الجديدة غير موصولة بعد

جسر Electron الحالي يحتوي وظائف مصادقة منفصلة، لكن لا بد من ربط شاشة الدخول بها، ثم استخدام هوية الجلسة في كل عمليات البيانات. لا يجوز تشغيل مسارين متوازيين يمنح كل منهما صلاحيات مختلفة.

## 6. خطة التنفيذ المقترحة

| المرحلة | العمل | شرط الإغلاق |
|---|---|---|
| INV-01 | استكمال الجرد الآلي واليدوي لكل مراجع Dexie وIndexedDB وlocalStorage | قائمة ملفات ومداخل قراءة وكتابة كاملة |

| QA-01 | اختبار تثبيت Windows وتشغيله وإغلاقه وإعادة تشغيل الجهاز والتحديث | إثبات بقاء نفس قاعدة البيانات والبيانات |

## 7. ما لا نعتبره إنجازًا حتى الآن

- لا نعتبر وجود ملف SQLite دليلًا على أن المبيعات والمشتريات والمخزون والمحاسبة تحفظ فيه.
- لا نعتبر نجاح بناء NSIS دليلًا على نجاح التثبيت والتشغيل على جهاز المستخدم.
- لا نعتبر نجاح اختبار استيراد عينة دليلًا على ترحيل قاعدة المستخدم الحقيقية.
- لا نعتبر شاشة مصادقة منفصلة دليلًا على ربط كل عمليات النظام بها.
- لا نحذف Dexie ولا ندمج PR#2 قبل اجتياز بوابات الاختبار أعلاه.

## 8. الخطوة البرمجية التالية

استكمال جرد كامل لمراجع Dexie في جميع ملفات الفرع، ثم تصميم واجهة قراءة وكتابة typed لطبقة SQLite مع اختبارات عقودها. بعد ذلك يبدأ النقل بمجال صغير منخفض المخاطر، ثم المجالات المالية بمعاملات ذرية ومطابقة أرصدة قبل وبعد كل مرحلة.
